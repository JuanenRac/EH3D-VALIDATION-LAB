# EH3D-VALIDATION-LAB: requirements

This register is the single source of the state of each capability. Status values: planned, prototype, implemented, validated. Four requirements are `prototype` (code and tests exist, only on data made by the tests) and two are `planned`; none has been used on a real corpus or validated. High test coverage is not proof of geometric or electrical correctness, so each requirement says how it will be checked and what result is expected.

| Requirement | Description | Status | How it will be checked | Expected result | Known limits |
|---|---|---|---|---|---|
| VLAB-001 | Run the corpus in redacted mode. | prototype | automatic: leak test | No string taken from the corpus appears in any report. | Reports of the gate and of the copy check hide case names and paths and are tested for leaks. The corpus commands (`corpus-inventory`, `corpus-copy`) print counts and digests only and are tested for leaks; the `oracle` command prints the names of the cases it is given, because its output is the input of the gate on the same machine, so keep that output out of any repository. |
| VLAB-002 | Golden-set manifest with checksums, verified against redundant copies. | prototype | automatic | A copy that differs from the manifest is reported. | Compares the bytes of folders; it cannot know that two copies are on different media. Only tried on data made by the tests. |
| VLAB-003 | Compare local results with the golden sets and classify each failure. | prototype | automatic | Every failure carries one of the three classes. | Results files must give the class of every failure (an unclassified failure is refused). The `oracle` command compares an observed file with a golden file check by check (each check belongs to a level) and writes the results the gate reads; a difference needs a class given by the person who looked at it. The values are compared as text: nothing here understands a design file, and the reader that fills the observed file belongs to the design tool. |
| VLAB-004 | Reduce a failing real project to a minimal anonymised case. | planned | automatic plus owner review | The reduced case contains no recognisable names, attributes or geometry. | Not started: no limits known yet. |
| VLAB-005 | Named tests for the model invariants, each linked to a requirement. | planned | automatic: property tests | Each invariant has at least one named test. | Not started: no limits known yet. |
| VLAB-006 | Gate: the measured rate of a level does not drop between runs. | prototype | automatic | A drop fails the gate and lists the new failures. | Rates are compared as exact fractions; the gate also fails on a case that used to pass and fails now, or that is missing (both can be switched off). Only tried on data made by the tests. |

Rules: a claim of correctness names the corpus, the tolerance and the tool version it holds for. A phase is complete when the measured rate does not drop, every failure is classified and fixed or documented, and the measured figure is reported.
